# 모델 선정 근거: 결과지 수치 추출

- 작성일: 2026-11-17
- 실험: [notebooks/poc.ipynb](../notebooks/poc.ipynb) (Google Colab, T4 GPU)
- 원본 결과: [results/](../results/) (`summary.csv`, `by_variant.csv`, `by_field.csv`, `failures.csv`, 방식별 예측 JSON)

## 1. 결론

**수치 추출은 Gemini Flash(`gemini-3.5-flash`)로 정한다.**
비교한 세 방식 중 성공 기준(필드 정확도 95% 이상)을 넘은 것은 Gemini뿐이고, 흐림·기울기·저해상도 사진에서도 120개 필드를 모두 맞혔다.

**OCR 모델만으로는 결과지를 해석할 수 없어서, OCR 능력이 내장된 비전 언어 모델(VLM)인 Gemini를 채택했다.**
OCR 모델(EasyOCR)은 글자를 읽을 수는 있지만, 한 장에 수십 개인 숫자 중 어느 것이 측정값이고 어느 것이 표준 범위·조절값인지는 사람이 만든 규칙으로 골라야 한다. 이 규칙은 사진이 조금만 기울거나 흐려도 무너져, 정확도가 깨끗한 사진 100%에서 흐린 사진 0%로 떨어졌다 (틀린 71개 중 59개가 값을 아예 찾지 못한 경우). Gemini는 글자 읽기와 표·그래프 구조 이해를 한 번에 해서 모든 촬영 조건에서 120개 필드를 모두 맞혔다.

다만 무료 등급의 응답 시간이 목표(10초)보다 길고, 사진이 외부 서버로 나가므로 실제 서비스 전에 아래 [5. 남은 과제](#5-남은-과제)를 해결해야 한다.

## 2. 비교 대상

| 방식 | 구성 | 고른 이유 |
|---|---|---|
| A. EasyOCR + 규칙 | 오픈소스 OCR로 글자를 읽고, "체중", "체지방률" 같은 라벨 옆 숫자를 규칙으로 고른다 | LLM 없이 얼마나 되는지 보는 **기준선** |
| B. Gemini Flash | 이미지와 프롬프트를 보내고 JSON 스키마(`response_schema`)로 8개 필드를 받는다 | 무료 등급이 있는 **상용 비전 API** |
| C. Qwen2.5-VL 3B | Colab GPU에서 직접 돌리는 오픈소스 비전 언어 모델, 같은 프롬프트 사용 | 사진을 **밖으로 보내지 않는** 로컬 방식 |
| (D. Claude 비전) | 코드만 노트북에 있음 | 유료라 이번 비교에서는 실행하지 않음 |

세 방식 모두 같은 가상 결과지 15장(필드 120개)과 같은 채점 규칙(결과지에 표시된 소수 자릿수로 반올림해 비교)을 쓴다.

## 4. 해석

### A. EasyOCR + 규칙: 깨끗한 사진에서만 쓸 수 있다
- 깨끗한 사진은 100%지만, 흐림·저해상도·복합에서는 0%다.
- 틀린 71개 중 **59개는 값을 아예 못 찾은 경우**다. OCR이 라벨 글자("체지방률" 등)를 잘못 읽으면 규칙이 숫자를 찾을 기준점을 잃는다.
- 기울어진 사진에서는 줄이 엇갈려 **체중 값이 체지방량 칸에 들어가는** 식의 밀림이 생긴다.
- 사용자가 폰으로 찍는 사진은 대부분 조금씩 기울거나 흐리므로 실서비스에는 맞지 않는다. 속도와 비용, 개인정보 면에서는 가장 좋아서 기준선으로 남긴다.

### B. Gemini Flash: 정확도는 충분하고, 속도와 전송이 과제다
- 모든 상태, 모든 필드에서 100%다. 표준 범위, 적정체중, 권장 섭취 열량 같은 헷갈리는 숫자에 한 번도 속지 않았다.
- **속도**: 중앙값 19.3초로 목표인 10초를 넘었다. 무료 등급이라 서버가 바쁠 때 503 응답과 재시도가 많았다. 같은 날 최신 `gemini-3.8-flash`는 장당 6분 넘게 걸려 `gemini-3.5-flash`로 바꿨다. 그래도 손으로 8개를 입력하는 약 2분보다는 6배 이상 빠르다.
- **외부 전송**: 체성분 결과는 개인 건강정보인데, 사진이 Google 서버로 나간다. 무료 등급은 약관상 입력이 서비스 개선에 쓰일 수 있다.
- **모델 교체가 잦다**: `gemini-2.5-flash`는 새 사용자에게 404가 나와서 쓸 수 없었다. 모델 이름을 설정값으로 빼 두고, 모델을 바꿀 때마다 이 노트북으로 다시 검증해야 한다.

### C. Qwen2.5-VL 3B: 사진을 지킬 수 있지만 아직 정확도가 부족하다
- 장당 5.5초로 B보다 빠르고 사진이 밖으로 나가지 않는다. 그림자가 진 사진에서는 100%다.
- 약점은 세 가지다.
  1. **막대그래프 속 숫자를 못 읽는다.** 체지방률은 결과지에서 표가 아니라 "비만분석" 막대그래프에만 나온다. C는 15장 중 7장에서 체지방률을 `null`로 냈다 (정확도 27%).
  2. **헷갈리는 숫자와 다른 필드 값을 가져온다.** 기초대사량 자리에 권장 섭취 열량(2,629)을, 골격근량 자리에 체중 표준 범위 하한(65.1)을 넣었다. 흐린 사진에서는 골격근량과 체지방량을 서로 바꿔 넣었다.
  3. **float16 출력 오류**: 첫 장에서 `!!!!…`만 출력했다. T4 GPU에서 float16으로 돌릴 때 생기는 수치 넘침 증상으로 보이며, 다시 실행해도 같았다.
- 라이선스(Qwen Research License)상 상업적 사용에 제한이 있어, 서비스에 쓰려면 다른 오픈소스 모델이나 라이선스를 다시 확인해야 한다.

## 5. 남은 과제

| 과제 | 방법 |
|---|---|
| 응답 시간 10초 이내 | 유료 등급이나 더 가벼운 모델(`flash-lite`)로 같은 노트북에서 다시 측정한다 |
| 건강정보 외부 전송 | 실서비스에서는 학습에 쓰이지 않는 유료 등급을 쓰고, 화면에서 "사진이 Google로 전송된다"는 동의를 받는다. 장기적으로는 로컬 모델(C 계열)을 개선해 대안으로 둔다 |
| 로컬 모델 개선 | 7B 모델, bfloat16·float32 실행, "체지방률은 막대그래프 옆 숫자" 같은 위치 힌트를 넣은 프롬프트로 다시 비교한다 |
| 실제 결과지 검증 | 가상 결과지 15장은 표본이 작고 실제 양식과 다르다. 동의를 받은 실제 결과지로 다시 평가한다 (개인정보 때문에 저장소에는 올리지 않는다) |

## 6. 재현 방법

1. Colab에서 [notebooks/poc.ipynb](../notebooks/poc.ipynb)를 열고 런타임을 T4 GPU로 바꾼다.
2. Colab Secrets에 `GEMINI_API_KEY`를 넣고 노트북 액세스를 켠다.
3. 위에서부터 차례로 실행한다. 결과는 `results/`에 저장된다.
4. 틀린 필드가 결과지의 어느 숫자에서 왔는지는 아래 명령으로 분류한다. 결과는 `results/failure_sources.csv`에 저장된다.
   ```
   node scripts/analyze_failures.mjs
   ```
