## 1. 성공 기준 달성 여부

[문제 정의서](problem_definition.md)의 성공 기준을, 선정한 방식(B. Gemini Flash)으로 확인했다.

| 항목 | 목표 | 결과 | 판정 |
|---|---|---|---|
| 핵심 8개 필드 추출 정확도 | 95% 이상 | **100%** (120/120) | 달성 |
| 입력 시간 (사진 → 수치) | 10초 이내 | 중앙값 **19.3초** (9.7~44.7초) | 미달. 손으로 입력할 때의 약 2분보다는 6배 빠르다 |

| 추천 운동의 도감 포함률 | 100% | **100%** (범용 챗봇식 62.4%) | 달성. [5. 루틴 추천 검증](#5-루틴-추천-검증) 참고 |

- C(Qwen 3B): 오류 1장을 뺀 깨끗한 사진 83% → 56% (저해상도)

## 3. 실패 사례

### 사례 1. 막대그래프에만 있는 숫자를 못 읽음 (C, 체지방률)

- **상황**: 체지방률은 결과지의 표에는 없고, "비만분석" 막대그래프 끝에만 숫자로 찍혀 있다.
- **결과**: C(Qwen 3B)는 15장 중 7장에서 체지방률을 `null`로 냈다. 깨끗한 사진(sample_02~04)에서도 그랬다. 체지방률 정확도는 27%로 다른 필드(67~93%)보다 크게 낮다.
- **원인 추정**: 작은 모델은 표 구조는 잘 따라가지만, 그래프 옆에 떨어져 있는 숫자를 라벨과 연결하지 못한다. 결과지에서 "체지방률"이라는 글자가 가장 또렷한 곳은 아래쪽 표준범위 줄("체지방률 10.0 ~ 20.0%")이라, 측정값이 없다고 판단한 것으로 보인다.
- **대응**: 프롬프트에 "체지방률은 비만분석 막대그래프 오른쪽 숫자"라는 위치 힌트를 넣거나 더 큰 모델(7B)로 다시 비교한다. 실서비스에서는 값이 비면 사용자에게 그 칸만 직접 입력하게 한다.

### 사례 2. 헷갈리는 숫자를 측정값으로 착각 (C)

결과지에 일부러 넣은 측정값이 아닌 숫자에 실제로 속았다.

| 파일 | 필드 | 정답 | 추출값 | 추출값의 정체 |
|---|---|---|---|---|
| sample_04_clean | 기초대사량 | 1,878 | 2,629 | "권장 섭취 열량" |
| sample_15_combo | 골격근량 | 31.4 | 65.1 | 체중 표준범위 하한 |
| sample_13_lowres | 체지방량 | 15.7 | 3.2 | 무기질 측정치 |
| sample_13_lowres | 체지방률 | 25.9 | 15.7 | 체지방량 (kg 값을 % 칸에 넣음) |
| sample_10_blur | 골격근량 / 체지방량 | 32.7 / 25.0 | 25.0 / 32.7 | 두 값이 서로 바뀜 |

- **원인 추정**: 깨끗한 사진(sample_04)에서도 생겼으므로 단순히 사진이 흐려서 생긴 문제가 아니다. 라벨이 비슷하거나("기초대사량" 근처의 다른 kcal 값) 숫자 범위가 그럴듯하면 엉뚱한 칸을 고른다.
- **의미**: 실제 결과지에도 표준 범위와 조절 목표 숫자가 섞여 있으므로, 이 유형이 실서비스에서 가장 위험하다. 값이 비어 있으면 사용자가 알아채지만, 그럴듯한 다른 숫자가 들어가면 모르고 지나간다.
- **대응**: 코드에서 값 사이의 관계를 검사한다. 예를 들어 체지방률 ≈ 체지방량 ÷ 체중 × 100, BMI ≈ 체중 ÷ 신장², 골격근량 < 체중이어야 한다. 어긋나면 그 필드를 사용자에게 확인받는다.

### 사례 3. 기울어진 사진에서 칸이 밀림 (A, 규칙 방식)

- **상황**: sample_05_tilt, sample_07_tilt (각각 6도, 8도 기울어짐)
- **결과**:
  - sample_05: 체중 칸은 비고, 체지방량 칸에 체중 값 73.0이 들어갔다.
  - sample_07: 체중 칸에 지방조절 값(-3.6), 골격근량 칸에 체중 값(66.3), 체지방량 칸에 무기질 값(3.4)이 들어가는 연쇄 밀림이 생겼다.
- **원인**: 규칙 방식은 "라벨과 같은 줄, 오른쪽에 있는 숫자"를 고른다. 사진이 기울면 OCR이 나눈 줄이 엇갈려 아래위 줄의 숫자가 붙는다. 흐림·저해상도에서는 라벨 글자 자체를 못 읽어서 값을 하나도 찾지 못했다 (A의 못 찾음 59개).
- **의미**: 규칙을 더 정교하게 만들어도 결과지 양식이나 촬영 각도가 바뀔 때마다 다시 고쳐야 한다. 이 방식을 주 방식으로 쓰지 않은 이유다.

### 추가: 로컬 모델의 float16 출력 오류 (C)

- sample_01_clean에서 C가 JSON 대신 `!!!!…`만 출력했고, 셀을 다시 실행해도 같았다.
- T4 GPU는 bfloat16을 제대로 지원하지 않아 float16으로 실행했는데, 이때 계산값이 넘쳐 의미 없는 토큰이 나오는 증상으로 보인다.
- 로컬 모델을 다시 비교할 때는 float32로 실행하거나 bfloat16을 지원하는 GPU에서 확인한다.

## 4. 이번 검증의 한계

- **표본이 작다.** 15장, 120개 필드다. B의 100%는 "이 가상 양식에서 틀린 적이 없다"는 뜻이지, 실제 결과지에서도 100%라는 뜻은 아니다.
- **가상 양식이다.** 실제 기기마다 배치, 글꼴, 그래프 모양이 다르다. 브랜드 양식을 베끼지 않으려고 자체 양식을 썼다.
- **무료 등급의 시간은 들쭉날쭉하다.** 같은 날에도 응답 시간이 장당 10초에서 45초까지 오갔고, 최신 모델은 6분이 넘었다. 시간 비교는 측정한 날의 서버 상태에 크게 좌우된다.
- **의료 조언이 아니다.** 이 PoC는 수치를 옮겨 적는 정확도와 운동 추천의 범위만 검증한다.

## 5. 루틴 추천 검증

- 실험: [notebooks/routine.ipynb](../notebooks/routine.ipynb)
- 입력: 1단계에서 Gemini가 추출한 15명의 수치 + 성별 (성별은 앱에서 사용자가 고른다)
- 모델: 두 방식 모두 `gemini-3.5-flash-lite`. 같은 날 `gemini-3.5-flash`는 무료 사용자가 몰려 루틴 하나에 234초가 걸려서 바꿨다. 두 방식에 같은 모델을 썼으므로 차이는 질문 방식에서 나온다.

| 방식 | 질문 방법 |
|---|---|
| 기준선 (범용 챗봇식) | 수치만 주고 "헬스장 입문자 주 3회 루틴을 짜 줘"라고 묻는다. ChatGPT 같은 챗봇에 결과지 수치를 붙여 넣는 상황이다 |
| 제안 방식 | 코드가 수치를 판정하고, 판정 결과 + 루틴 규칙 + **도감 운동 ID 목록**을 준다. 응답의 ID를 코드에서 도감과 다시 대조해 지운다 |

### 도감 포함률

| 방식 | 도감 포함률 | 도감 밖 운동이 있는 루틴 | 평균 응답 시간 |
|---|---|---|---|
| 기준선 (범용 챗봇식) | **62.4%** | **15/15** | 2.6초 |
| 제안 방식 (필터 전) | **100%** | 0/15 | 5.6초 |
| 제안 방식 (필터 후) | 100% | 0/15 | |

- 기준선은 15명 **모두**의 루틴에 도감에 없는 운동이 들어갔다. 추천 운동 10개 중 4개는 사용자가 도감에서 자세를 확인할 수 없다.
- 기준선 채점은 일부러 너그럽게 했다. 띄어쓰기와 "머신"을 빼고 도감 운동 이름이 들어 있으면 포함으로 셌다 (예: "덤벨 숄더 프레스"도 "숄더 프레스"로 포함). 실제 포함률은 62.4%보다 낮다.
- 제안 방식은 LLM이 처음부터 도감 ID만 냈다. 코드 필터는 이번에는 지운 것이 없지만, 모델이 바뀌거나 프롬프트가 길어질 때를 대비한 안전장치로 남긴다.
- 제안 방식이 3초 더 걸리는 것은 프롬프트에 규칙과 운동 목록 20개가 들어가 입력이 길기 때문이다.

### 기준선이 추천한 도감 밖 운동 (자주 나온 순)

| 운동 | 횟수 | 도감에 없는 이유 |
|---|---|---|
| 플랭크 | 13 | 맨몸 운동. 도감은 기구 운동만 다룬다 |
| 덤벨 스쿼트, 덤벨 런지, 인클라인 덤벨 프레스 | 4, 2, 3 | 덤벨(프리웨이트) 운동 |
| 바벨 스쿼트, 데드리프트, 오버헤드 프레스 | 3, 3, 2 | 바벨 운동. 입문자에게 자세 부담이 크다 |
| 런지, 레그 레이즈, 푸시업 | 3, 3, 2 | 맨몸 운동 |
| 사이클, 트레드밀 걷기, 천국의 계단 | 3, 2, 4 | 유산소 기구. 도감에 없다 |

범용 챗봇은 "헬스장에 흔히 있는 운동"을 추천할 뿐, 사용자가 자세를 확인할 수 있는 도감의 범위를 모른다. 문제 정의서의 문제 4("일반 챗봇의 추천은 내 환경과 맞지 않는다")가 실제로 확인됐다.

### 루틴 규칙 준수율 (제안 방식, 15명)

| 규칙 | 준수율 |
|---|---|
| 3일 구성 | 100% |
| 하루 4~6개 | 100% |
| 같은 날 중복 없음 | 100% |
| 2~4세트 | 100% |
| 8~15회 | 100% |
| 가슴·등·하체 포함 | 100% |
| 체지방률 높음 → 유산소 안내 | 100% |

규칙을 어긴 루틴은 없었다.

### 사례 4. 형식은 지켰지만 목표가 한쪽만 반영됨 (제안 방식)

- **상황**: sample_01 (여성, 체지방률 38%·BMI 29.6 높음, 근육량 낮음 → 목표 "근육량 늘리기 + 체지방 줄이기")
- **결과**: 15개 운동이 **모두 3세트 × 12~15회**였다. 규칙상 근육량 늘리기는 "복합 운동을 앞에 두고 8~12회 3~4세트"인데, 체지방 줄이기 쪽 기준(12~15회)만 따랐다. 프리처 컬처럼 작은 근육 운동이 하루의 마지막을 채우기도 했다.
- **잘한 점**: BMI가 높아 레그 프레스·백 익스텐션처럼 관절 부담이 적은 머신을 골랐고, 복근 운동에 "부분 감량은 안 된다"는 설명을 붙였고, 유산소 안내도 넣었다.
- **한 명만의 문제가 아니다**: 목표가 "근육량 늘리기 + 체지방 줄이기"인 6명의 운동 78개 중 64개(82%)가 12회 이상이었다. 8~12회 위주로 짠 사람은 없었다 (`results/routine_ours.json`).
- **원인 추정**: 목표가 두 개일 때 어느 쪽을 어떻게 섞을지 규칙에 없다. 형식 검사(2~4세트, 8~15회)는 범위만 보므로 이런 쏠림을 잡지 못한다.
- **대응**: 복합 목표일 때 "Day마다 앞쪽 복합 운동 2개는 8~12회, 나머지는 12~15회"처럼 규칙을 구체화하고, 목표별로 기대하는 반복 범위를 코드에서 검사한다.
- **덧붙여 찾은 표시 오류**: 모델이 반복 수를 "12~15"와 "12~15회"로 섞어 보내서 화면에 "12~15회회"가 나왔다. 노트북과 헬스도감 앱 모두 표시할 때 단위를 한 번만 붙이도록 고쳤다 (프롬프트는 평가 결과와 같게 유지).

### 루틴 추천의 한계

- **규칙 검사는 형식만 본다.** 세트·횟수·부위 구성은 코드로 검사했지만, 추천 이유(`reason`)가 적절한지, 운동 순서가 좋은지는 사람이 보지 않았다. 트레이너 검토나 사용자 평가가 다음 단계다.
- **도감에 유산소·맨몸 운동이 없다.** 체지방을 줄여야 하는 사용자에게 유산소는 운동 목록이 아니라 안내 문구로만 줄 수 있다. 도감에 유산소 기구를 추가하면 루틴에 넣을 수 있다.
- **판정 기준이 단순하다.** 골격근량 ÷ 체중 같은 PoC용 기준이라 키·나이를 반영하지 않는다. 실제 기기의 표준 범위를 결과지에서 함께 읽어 쓰는 방법을 검토한다.
- **모델이 다르다.** 수치 추출은 `gemini-3.5-flash`로 검증했고, 루틴은 `gemini-3.5-flash-lite`로 검증했다. 헬스도감 앱은 기본 모델이 바쁘면 lite로 넘어가는데, lite의 **수치 추출 정확도는 아직 검증하지 않았다.**
