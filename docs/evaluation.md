# 검증 결과와 실패 사례

- 작성일: 2026-11-17
- 대상: 가상 체성분 결과지 15장 (깨끗함 4, 기울기 3, 흐림 3, 그림자 2, 저해상도 2, 복합 1), 핵심 필드 120개
- 방식별 상세 비교와 선정 근거는 [model_comparison.md](model_comparison.md)에 있다.

## 1. 성공 기준 달성 여부

[문제 정의서](problem_definition.md)의 성공 기준을, 선정한 방식(B. Gemini Flash)으로 확인했다.

| 항목 | 목표 | 결과 | 판정 |
|---|---|---|---|
| 핵심 8개 필드 추출 정확도 | 95% 이상 | **100%** (120/120) | 달성 |
| 입력 시간 (사진 → 수치) | 10초 이내 | 중앙값 **19.3초** (9.7~44.7초) | 미달. 손으로 입력할 때의 약 2분보다는 6배 빠르다 |
| 흐린·기울어진 사진 | 하락 폭 측정 | 모든 상태에서 100%, **하락 없음** | 측정 완료 |
| 추천 운동의 도감 포함률 | 100% | 루틴 추천 단계에서 측정 예정 | 진행 중 |

비교용 방식의 하락 폭은 다음과 같다. 깨끗한 사진 대비 가장 나쁜 상태를 기준으로 했다.
- A(EasyOCR+규칙): 100% → 0% (흐림·저해상도·복합)
- C(Qwen 3B): 오류 1장을 뺀 깨끗한 사진 83% → 56% (저해상도)

## 3. 실패 사례

### 사례 1. 막대그래프에만 있는 숫자를 못 읽음 (C, 체지방률)

- **상황**: 체지방률은 결과지의 표에는 없고, "비만분석" 막대그래프 끝에만 숫자로 찍혀 있다.
- **결과**: C(Qwen 3B)는 15장 중 7장에서 체지방률을 `null`로 냈다. 깨끗한 사진(sample_02~04)에서도 그랬다. 체지방률 정확도는 27%로 다른 필드(67~93%)보다 크게 낮다.
- **원인 추정**: 작은 모델은 표 구조는 잘 따라가지만, 그래프 옆에 떨어져 있는 숫자를 라벨과 연결하지 못한다. 결과지에서 "체지방률"이라는 글자가 가장 또렷한 곳은 아래쪽 표준범위 줄("체지방률 10.0 ~ 20.0%")이라, 측정값이 없다고 판단한 것으로 보인다.
- **대응**: 프롬프트에 "체지방률은 비만분석 막대그래프 오른쪽 숫자"라는 위치 힌트를 넣거나 더 큰 모델(7B)로 다시 비교한다. 실서비스에서는 값이 비면 사용자에게 그 칸만 직접 입력하게 한다.

### 사례 2. 헷갈리는 숫자를 측정값으로 착각 (C)

결과지에 일부러 넣은 측정값이 아닌 숫자에 실제로 속았다.

| 파일 | 필드 | 정답 | 추출값 | 추출값의 정체 |
|---|---|---|---|---|
| sample_04_clean | 기초대사량 | 1,878 | 2,629 | "권장 섭취 열량" |
| sample_15_combo | 골격근량 | 31.4 | 65.1 | 체중 표준범위 하한 |
| sample_13_lowres | 체지방량 | 15.7 | 3.2 | 무기질 측정치 |
| sample_13_lowres | 체지방률 | 25.9 | 15.7 | 체지방량 (kg 값을 % 칸에 넣음) |
| sample_10_blur | 골격근량 / 체지방량 | 32.7 / 25.0 | 25.0 / 32.7 | 두 값이 서로 바뀜 |

- **원인 추정**: 깨끗한 사진(sample_04)에서도 생겼으므로 단순히 사진이 흐려서 생긴 문제가 아니다. 라벨이 비슷하거나("기초대사량" 근처의 다른 kcal 값) 숫자 범위가 그럴듯하면 엉뚱한 칸을 고른다.
- **의미**: 실제 결과지에도 표준 범위와 조절 목표 숫자가 섞여 있으므로, 이 유형이 실서비스에서 가장 위험하다. 값이 비어 있으면 사용자가 알아채지만, 그럴듯한 다른 숫자가 들어가면 모르고 지나간다.
- **대응**: 코드에서 값 사이의 관계를 검사한다. 예를 들어 체지방률 ≈ 체지방량 ÷ 체중 × 100, BMI ≈ 체중 ÷ 신장², 골격근량 < 체중이어야 한다. 어긋나면 그 필드를 사용자에게 확인받는다.

### 사례 3. 기울어진 사진에서 칸이 밀림 (A, 규칙 방식)

- **상황**: sample_05_tilt, sample_07_tilt (각각 6도, 8도 기울어짐)
- **결과**:
  - sample_05: 체중 칸은 비고, 체지방량 칸에 체중 값 73.0이 들어갔다.
  - sample_07: 체중 칸에 지방조절 값(-3.6), 골격근량 칸에 체중 값(66.3), 체지방량 칸에 무기질 값(3.4)이 들어가는 연쇄 밀림이 생겼다.
- **원인**: 규칙 방식은 "라벨과 같은 줄, 오른쪽에 있는 숫자"를 고른다. 사진이 기울면 OCR이 나눈 줄이 엇갈려 아래위 줄의 숫자가 붙는다. 흐림·저해상도에서는 라벨 글자 자체를 못 읽어서 값을 하나도 찾지 못했다 (A의 못 찾음 59개).
- **의미**: 규칙을 더 정교하게 만들어도 결과지 양식이나 촬영 각도가 바뀔 때마다 다시 고쳐야 한다. 이 방식을 주 방식으로 쓰지 않은 이유다.

### 추가: 로컬 모델의 float16 출력 오류 (C)

- sample_01_clean에서 C가 JSON 대신 `!!!!…`만 출력했고, 셀을 다시 실행해도 같았다.
- T4 GPU는 bfloat16을 제대로 지원하지 않아 float16으로 실행했는데, 이때 계산값이 넘쳐 의미 없는 토큰이 나오는 증상으로 보인다.
- 로컬 모델을 다시 비교할 때는 float32로 실행하거나 bfloat16을 지원하는 GPU에서 확인한다.

## 4. 이번 검증의 한계

- **표본이 작다.** 15장, 120개 필드다. B의 100%는 "이 가상 양식에서 틀린 적이 없다"는 뜻이지, 실제 결과지에서도 100%라는 뜻은 아니다.
- **가상 양식이다.** 실제 기기마다 배치, 글꼴, 그래프 모양이 다르다. 브랜드 양식을 베끼지 않으려고 자체 양식을 썼다.
- **무료 등급의 시간은 들쭉날쭉하다.** 같은 날에도 응답 시간이 장당 10초에서 45초까지 오갔고, 최신 모델은 6분이 넘었다. 시간 비교는 측정한 날의 서버 상태에 크게 좌우된다.
- **의료 조언이 아니다.** 이 PoC는 수치를 옮겨 적는 정확도와 운동 추천의 범위만 검증한다.
